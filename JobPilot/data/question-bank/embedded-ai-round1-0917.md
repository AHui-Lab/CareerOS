## 第1题（C/C++ · malloc/free 与 new/delete）

**题目：** C 中的 malloc/free 和 C++ 中的 new/delete 有什么区别？

**考察点：**
- 是否理解"库函数 vs 运算符"的语言层面差异
- 核心区别能否点到：构造/析构的调用（类语义），而不是只背语法差异
- 是否知道失败行为、数组版本、配对纪律等工程细节

**回答建议（嵌入式工程师角度）：**

主要六个区别，逐层展开：

1. **语言层面**：malloc/free 是 C 标准库函数（stdlib.h）；new/delete 是 C++ 运算符，支持重载——可以重载来自定义分配策略，比如做内存池（嵌入式常用手段）。
2. **类型安全**：malloc 返回 `void*`，必须手动强制转换；new 返回具体类型指针，大小由编译器按类型自动计算。
3. **构造与析构（最核心）**：malloc 只分配原始内存；new 先分配内存再调用构造函数，delete 先调用析构函数再释放。对 POD 类型两者效果接近，对类类型完全不同。
4. **失败行为**：malloc 失败返回 NULL；new 失败默认抛出 bad_alloc 异常，除非用 `new (nothrow)` 才返回 NULL。
5. **数组配套**：`new[]` 必须配 `delete[]`，会逐个析构；malloc/free 没有数组语义。
6. **底层实现**：new/delete 的默认版本通常基于 malloc/free 实现。

收尾强调使用纪律：malloc↔free、new↔delete、new[]↔delete[] 必须严格配对，混用是未定义行为。嵌入式加分句：「我的项目习惯高频路径静态分配，必须动态时用固定大小内存池 + 堆水位监控」。

**HR/面试官视角评价：**
- ✅ 加分信号：把"构造/析构"放在最核心位置讲；提到运算符重载做内存池，体现工程化思维
- ❌ 减分信号：只罗列"malloc 要计算大小、new 不用"这类语法差异，说不清析构语义——暴露只用过没理解过

## 第2题（C/C++ · 悬挂指针）

**题目：** 为什么 free 之后要将指针指向 NULL？如果不指向 NULL 会出什么问题？（追问：为什么不指向 NULL 会出问题？）

**考察点：**
- 是否真正理解 free 的语义：释放的是内存，指针变量的值不变
- 对 double free 和 use-after-free 两类风险及其后果的认知
- 能否上升到"fail-fast"设计思想和工程预防手段

**回答建议（嵌入式工程师角度）：**

free 只把内存归还给堆管理器，**指针变量本身的值不变**，它仍保存着那块内存的地址——这就是**悬挂指针（dangling pointer）**。不置 NULL 有两类风险：

1. **二次释放（double free）**：后续代码路径再次 free 同一指针，破坏堆管理结构。glibc 会检测并报 "double free or corruption" abort；在没有这种保护的嵌入式环境，直接表现为堆损坏、偶发死机，且故障点远离根因、极难复现。
2. **释放后使用（use-after-free）**：指针看起来仍有效，后续误用它读写已释放内存。最阴险的是刚 free 完那块内存还没被复用，**读出来的值"看起来是对的"**——bug 潜伏到内存被重新分配后才爆发，现象与根因相距很远。

置 NULL 的保护是双重的：① **free(NULL) 是标准保证的安全空操作**，double free 变成无害调用；② 解引用 NULL 立刻崩溃（段错误 / MCU 上 HardFault）——**故障点即错误点**，马上能定位。

一句话总结：**置 NULL 把"随机延时爆炸"变成"立即确定爆炸"**，是 fail-fast 设计思想。

延伸：C++ 用智能指针（unique_ptr/shared_ptr + RAII）从机制上消灭悬挂指针；嵌入式实践则尽量静态分配，从源头减少 free 的出现。

**HR/面试官视角评价：**
- ✅ 加分信号：能说出"读到的值看起来正常所以 bug 潜伏"——说明真踩过或真理解；总结出 fail-fast
- ❌ 减分信号：只答"防止野指针"四个字，说不清 double free 和 UAF 各自的机理和后果

## 第3题（数据结构 · 链表效率优化）

**题目：** 链表如何提高查找和删除这些操作的效率？

**考察点：**
- 是否先分操作讨论（查找 O(n) 是痛点 vs 删除 O(1)/O(n) 的条件），体现结构化思维
- 方案的多样性：哈希索引、跳表、双向链表、LRU 组合结构
- 有无工程视角（缓存局部性、嵌入式静态节点池）

**回答建议（嵌入式工程师角度）：**

先按操作拆开：链表的痛点是**查找 O(n)**；删除在已知节点时是 O(1)，但单向链表找前驱要 O(n)。所以"提效"分两个方向：

**提高查找效率：**
1. **哈希表做索引**：哈希表维护 key → 节点指针映射，查找 O(1)；链表保留插入/顺序语义。代价是空间换时间。
2. **跳表（Skip List）**：有序链表上建多层索引，查找 O(log n)，实现简单且支持范围查询——Redis 有序集合的底层结构。
3. 工程视角：嵌入式小规模场景直接换**数组 + 下标**，利用缓存局部性反而更快——链表节点分散、cache miss 多，这是常被忽略的点。

**提高删除效率：**
1. **双向链表**：已知节点时删除 O(1)，不用找前驱。
2. **哈希 + 双向链表组合**：查找 O(1) 定位节点 + 双向链表 O(1) 摘除——这就是 **LRU 缓存的标准实现**（LeetCode 146），也是嵌入式缓存/资源池管理的常用结构。
3. 惰性删除：先打标记，批量回收时统一摘链。

**HR/面试官视角评价：**
- ✅ 加分信号：开头先分操作拆解；给出"哈希+双向链表=LRU"的组合方案并知道适用场景
- ❌ 减分信号：只说"用哈希"三个字答不出结构细节；不知道跳表这种替代方案的存在

## 第4题（数据结构 · 哈希索引正确性）

**题目：** （追问上题）用哈希的话，如何保证索引的正确性？

**考察点：**
- 本场深挖题：从"知道用哈希"追到"哈希体系自身的正确性"
- 四个层次：定位与比对、冲突处理、索引与数据一致性、rehash 一致性
- 能否联系指针生命周期（悬挂索引 = use-after-free 的变体）

**回答建议（嵌入式工程师角度）：**

"索引正确性"有四层含义，分层作答：

1. **哈希定位 + key 精确比对（两级查找）**：哈希值只做粗匹配定位到桶，**桶内必须存完整 key 做精确比较**——不同 key 可能 hash 相同，只比 hash 会误匹配。这是"先定桶、再比对"的标准两级查找。
2. **冲突处理**：拉链法（桶内挂链表，超长转红黑树，如 Java HashMap 阈值 8）或开放地址法（线性探测/双重散列）；负载因子超阈值要扩容。
3. **索引与链表本体的一致性（与上题结合的关键）**：哈希表存的是链表节点指针，链表任何增删必须**双写同步**更新哈希表——删除节点时**先删哈希条目、再释放节点内存**，顺序反了会出现**悬挂索引**：哈希返回已释放的指针，后续访问就是 use-after-free。与第 2 题的 free 置 NULL 是同一类问题：指针有效性由谁保证。
4. **rehash 时的一致性**：扩容重分布期间读写会错乱。策略：一次性 rehash（短暂锁表）或**渐进式 rehash**（Redis 方案：新旧双表并存，每次操作搬一批，读时先查旧表再查新表）。

嵌入式加分句：「我用静态节点池 + 哈希索引代替动态分配，节点生命周期由池管理，索引一致性用『先移除索引、后回收节点』的固定顺序保证。」

**HR/面试官视角评价：**
- ✅ 加分信号：能把"悬挂索引"和"use-after-free"打通——跨知识点连接是理解深度的标志
- ❌ 减分信号：只答"哈希冲突用链表解决"一层就停——本题是追问链，答一层会被继续追问到哑火（本场实际情况）

## 第5题（网络编程 · Socket 系统调用）

**题目：** TCP Socket 通信中会涉及哪些系统调用？

**考察点：**
- 服务端 socket→bind→listen→accept→read/write→close 五步流程是否扎实
- 客户端流程与 connect 的握手语义
- 关键认知：三次握手由内核协议栈完成，accept 只是从全连接队列取连接

**回答建议（嵌入式工程师角度）：**

**服务端**五个关键调用：
1. `socket(AF_INET, SOCK_STREAM, 0)`——创建套接字，返回文件描述符；
2. `bind(fd, 地址结构, len)`——绑定本地 IP 和端口；
3. `listen(fd, backlog)`——进入监听，内核创建**半连接队列**（收到 SYN、握手未完成）和**全连接队列**（握手完成的连接）；
4. `accept(listenfd)`——从全连接队列**取出一个已完成连接**，返回新的连接 fd；监听 fd 继续监听，连接 fd 用来收发数据；
5. `read/recv`、`write/send` 收发，`close()` 关闭。

**客户端**：`socket()` → `connect()`（发起三次握手，阻塞至握手完成或超时失败）→ 收发 → `close()`。

辅助调用：`setsockopt`（如 SO_REUSEADDR 解决重启时端口占用）、`fcntl` 设非阻塞。

必须讲出的加分认知：「三次握手是**内核协议栈**完成的，不是 accept 完成的——accept 只是消费者，从全连接队列取货。」多数候选人分不清这层。

**HR/面试官视角评价：**
- ✅ 加分信号：能区分监听 fd 和连接 fd 的角色；点出"握手是内核做的"
- ❌ 减分信号：漏 bind 或 listen；说不清 accept 与握手的关系（本题是第 6 题追问的铺垫）

## 第6题（网络编程 · accept 阻塞行为）

**题目：** （追问上题）调用 accept 的时候还没有客户端发起连接的话，内核会怎么处理？

**考察点：**
- 阻塞/非阻塞两种模式下的内核行为（睡眠挂等待队列 vs EAGAIN）
- 有无内核视角：等待队列、半连接/全连接队列、SYN flood 与 syncookies

**回答建议（嵌入式工程师角度）：**

分两种模式：

1. **默认阻塞模式**：当前进程被置为睡眠，挂到监听 socket 的**等待队列**上，不消耗 CPU；直到全连接队列来了新连接（或收到信号）才被唤醒，accept 返回新的连接 fd。
2. **非阻塞模式**（fd 设置了 O_NONBLOCK）：accept 立即返回 -1，errno 置为 **EAGAIN / EWOULDBLOCK**，调用方需要轮询——更常见的做法是配合 IO 多路复用，等"监听 fd 可读"事件再调 accept。

补充安全相关点：半连接队列积压与 SYN flood 攻击有关，内核的 syncookies 机制可以缓解——说明我理解 accept 上下游的内核行为，而不只是背 API。

**HR/面试官视角评价：**
- ✅ 加分信号：说清"睡眠挂队列、不耗 CPU"；主动提到非阻塞 + 多路复用的配合关系
- ❌ 减分信号：答"accept 会一直等"就没了，说不出等待队列和 EAGAIN 的机制名词

## 第7题（网络编程 · 多客户端并发方案）

**题目：** （继续追问）服务端想要处理多个客户端连接，有什么方案？

**考察点：**
- 四代方案的演进逻辑：多进程 → 多线程 → IO 多路复用 → 事件驱动框架
- select/poll/epoll 的对比精度（上限、复杂度、数据结构）
- LT/ET 模式差异与工程约束（ET 必须非阻塞 + 读写到 EAGAIN）

**回答建议（嵌入式工程师角度）：**

按演进讲，每代解决前一代的瓶颈：

1. **多进程**：主进程 accept 后 fork 子进程处理连接。隔离性好（一个崩不影响别人），但开销大、切换贵；注意父进程 close 连接 fd、子进程 close 监听 fd，并用 wait/SIGCHLD 回收僵尸进程。
2. **多线程**：每连接一个线程，切换开销小，但需同步保护共享数据；工程上用**线程池**避免频繁创建销毁。
3. **IO 多路复用**：单（少）线程监视一批 fd，就绪才处理：
   - `select`：fd_set 位图，1024 个 fd 上限，每次调用整体拷贝并重置集合，返回后 O(n) 遍历找就绪者；
   - `poll`：pollfd 数组，去掉 1024 限制，仍 O(n) 遍历；
   - `epoll`（Linux 特有）：内核用**红黑树**管理 fd、**就绪链表**回调通知，返回的就是就绪事件列表；分 LT（水平触发，默认）和 **ET（边缘触发，必须配非阻塞 fd 并读写到 EAGAIN，否则丢事件）**；海量并发下优势明显。
4. **事件驱动框架 / Reactor**：libevent、libuv 把多路复用 + 回调封装成事件循环；Redis、Nginx 的通用形态。

嵌入式视角收尾：资源受限设备倾向**单线程 epoll/select + 每连接一个状态机**，避免线程栈的内存开销——与协议解析状态机是同一套思路。

**HR/面试官视角评价：**
- ✅ 加分信号：演进式叙述体现取舍思维；epoll 红黑树/就绪链表、ET 的 EAGAIN 细节张口就来
- ❌ 减分信号：只罗列名词说不出 select 和 epoll 的本质差异；不知道 ET 模式的使用约束

## 第8题（操作系统 · 进程与线程）

**题目：** 进程和线程的区别？

**考察点：**
- 基本盘概念题：资源分配单位 vs 调度单位的核心定位
- 六个维度的完整度：地址空间、切换开销、通信、健壮性、实现视角
- 能否关联嵌入式（RTOS 任务更接近线程）

**回答建议（嵌入式工程师角度）：**

六个维度：
1. **本质定位**：进程是**资源分配**的基本单位，线程是 **CPU 调度**的基本单位。
2. **地址空间**：进程地址空间独立；同进程内线程共享代码段、数据段、堆，各自拥有私有栈和寄存器上下文。
3. **切换开销**：进程切换要换页表基址、TLB 大面积失效；同进程线程切换只换栈指针和寄存器，开销小得多。
4. **通信方式**：进程间靠 IPC（管道、消息队列、共享内存、信号量、socket）；线程间直接读写共享变量，配互斥锁、条件变量同步。
5. **健壮性**：进程隔离，一个崩溃不影响别人；一个线程崩溃整个进程挂掉。
6. **实现视角**：Linux 上线程是共享资源的轻量级进程（task_struct + CLONE_VM 等 clone 标志，NPTL）；RTOS 里的任务概念更接近线程——同一地址空间内调度。

**HR/面试官视角评价：**
- ✅ 加分信号：从"资源 vs 调度"的定位切入而不是背特征列表；提到 TLB/页表层面的切换开销
- ❌ 减分信号：只说"进程大线程小"这类模糊表述；漏掉共享内容里"栈是私有"的关键细节

## 第9题（操作系统 · 进程线程退出差异）

**题目：** （追问上题）进程和线程退出的时候有什么不同？

**考察点：**
- 本场追问链的深水区：僵尸进程与 wait 收割、pthread_join 与 detached
- 进程退出 = 整体回收 + 留状态等父进程；线程退出 = 只收私有资源
- 主线程 return 会杀全进程 vs pthread_exit 只退自己——边界情况认知

**回答建议（嵌入式工程师角度）：**

**进程退出**：
- 路径：`exit()` 先执行 atexit 注册的清理函数、冲洗 stdio 缓冲，再陷入内核；`_exit()` 直接陷入内核。
- 内核**整体回收**地址空间、页表、文件描述符等全部资源。
- 关键：退出后不是立刻消失，而是进入**僵尸态（Zombie）**——PCB 保留退出状态码，等**父进程 wait()/waitpid() 收割**；不收就一直占进程表项，泄漏资源。
- 父进程先死则变**孤儿进程**，被 1 号进程（init/systemd）收养并回收；退出时内核向父进程发 SIGCHLD。

**线程退出**：
- `pthread_exit()` 或线程函数 return；注意**主线程 return 会触发 exit 杀掉整个进程的所有线程**，而主线程调 pthread_exit 只退出自己、其他线程继续。
- 只回收线程**私有**资源：栈、寄存器上下文、TLS；**共享的堆和全局数据不动**——进程还活着。
- joinable 线程必须被 `pthread_join()` 回收（类似进程的 wait，还能取返回值），不 join 资源不释放；detached 线程退出后系统自动回收。
- 线程退出**没有内建的"通知其他线程"机制**，需要条件变量/信号量自行协调。

一句话对照：**进程退出 = 整体回收 + 留退出状态等父进程 wait；线程退出 = 只收私有栈 + 等（或不等）同进程 join，共享资源不动。**

**HR/面试官视角评价：**
- ✅ 加分信号：僵尸/孤儿/wait 这组概念链完整；说出"主线程 return 杀全家"的边界情况
- ❌ 减分信号：只答"进程退出释放所有资源、线程退出不释放"，说不清僵尸态和 join 机制——本题正是用来区分背书和理解的

## 第10题（硬件接口 · 电平转换）

**题目：** 主控 3.3V、外设需要 5V，在 SPI 和 I2C 这两种通信方式中如何进行电平转换？

**考察点：**
- 是否先分析信号方向性（SPI 单向 vs I2C 双向开漏）再给方案
- 方案完整度：专用芯片 / MOS 分立 / 分压 / 直连兼容判断
- 选型时的工程判断（速率、成本、VIH/VIL 核对手册）

**回答建议（嵌入式工程师角度）：**

先看方向性，两种总线不一样：
- **SPI**：SCK、MOSI、CS 单向（主→从，3.3→5V），**MISO 单向（从→主，5→3.3V）**——单向转换好办；
- **I2C**：SDA/SCL 都是**双向开漏**，任何一端都可能拉低总线——必须双向方案。

四个方案：
1. **专用电平转换芯片（量产首选）**：双电源收发器 74LVC1T45 / 74LVC245（适合 SPI，方向引脚控制）；自动感方向的 TXS0108E；I2C 专用双向 PCA9302。高速 SPI（>10MHz）必须走这类。
2. **MOS 管分立方案（I2C 经典）**：每根线一个 BSS138 + 两侧上拉（低压侧 3.3V、高压侧 5V）。成本最低，100k/400k I2C 够用。原理见下题。
3. **电阻分压（仅 5V→3.3V 方向，如 MISO）**：代价是 RC 时间常数限制速度、静态功耗、驱动能力弱；低速低成本场合凑合。
4. **直连（先查手册，可能不用转）**：5V 器件输出 → 3.3V 主控，看引脚是否 **5V 容忍（FT）**——STM32 带 FT 标注的 GPIO 可直接接；3.3V 输出 → 5V 器件，看 VIH：TTL 电平输入（VIH≈2.0V，74HCT 系列）可直接驱动，CMOS 输入（VIH≈3.5V）不行。I2C 技巧：**上拉直接接 3.3V**，总线高电平即 3.3V，只要 5V 器件 VIH 低于 3.3V 可直连（需核对手册）。

**HR/面试官视角评价：**
- ✅ 加分信号：开口先分方向性再谈方案；知道查 VIH/FT 判断能否直连——真实硬件调试经验的味道
- ❌ 减分信号：只答"用电平转换芯片"，说不出 SPI 与 I2C 方向性差异、没有选型逻辑

## 第11题（硬件接口 · I2C 与二极管）

**题目：** （追问上题）I2C 总线能不能接二极管进行电平转换？

**考察点：**
- 结论 + 根因：二极管单向导通 vs I2C 双向开漏的根本矛盾
- 第二层：导通压降抬高 VIL、吃掉噪声容限
- 高分项：讲清 MOS 管电路双向工作的三态原理（含体二极管作用）

**回答建议（嵌入式工程师角度）：**

**不能，核心原因是二极管是单向器件，而 I2C 是双向开漏总线。**

SDA/SCL 上任何一方都可能拉低总线：串了二极管后，一侧拉低无法传导到另一侧，通信直接不成立。二极管方案只能考虑用于已知单向的信号。

即使对单向信号，二极管串联还有第二个问题：**导通压降抬高低电平**。硅管 0.7V、肖特基约 0.3V，低电平经过二极管后被抬高，接收方的 **VIL 噪声容限被吃掉**，超过 VIL 上限就会识别错误或处于不定态。

**正确答案是 MOS 管电路**（BSS138：栅极接 3.3V，源极接 3.3V 侧上拉，漏极接 5V 侧上拉），双向工作原理：
- **静态两边都高**：Vgs = 0，MOS 截止，两边靠各自上拉维持高电平，互相隔离，5V 不倒灌 3.3V 侧；
- **3.3V 侧拉低**：源极变 0，Vgs ≈ 3.3V 大于开启电压，MOS 导通 → 5V 侧被拉低；
- **5V 侧拉低**：**体二极管**先导通，把源极拖到约 0.7V，此时 Vgs 足够使沟道导通，进一步把源极压到接近 0——两边都为低。

所以 MOS 方案天然双向、任一侧拉低都能传导，这是它能用于 I2C 而二极管不行的根本原因。

**HR/面试官视角评价：**
- ✅ 加分信号：结论先行再给两层根因；能展开体二极管先导通、沟道再拉低的两段动作——硬件理解到器件级
- ❌ 减分信号：只答"不行"说不出双向开漏这个根因；不知道 MOS 电路为什么可以双向
