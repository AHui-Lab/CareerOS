## 第1题（项目深挖 · RAG）

**题目：** 针对你的 RAG 项目深问——对不同类型（格式）的文件如何处理？如何分类处理？它们之间的关系（关联）如何处理？

**考察点：**
- 是否真正动手做过数据预处理 pipeline，而非只调过现成框架
- 对多模态/多格式文档的工程化理解（PDF、Word、Excel、图片、扫描件、网页等）
- 是否具备"知识结构化"思维：chunk 之间、文档之间的语义关联如何保留

**回答建议（产品经理角度）：**

1. **先讲分类逻辑，再讲处理细节**——体现结构化思维：
   - 按**格式**分：结构化（Excel/表格/数据库导出）、半结构化（HTML/Markdown/带层级的 Word）、非结构化（纯文本 PDF/扫描件/图片）
   - 按**业务属性**分：制度文件、操作手册、FAQ、合同条款等——分类不是技术动作，是为了后续差异化的 chunk 策略和检索路由

2. **分类型处理策略（举例说明，带上你项目里的真实选择）：**
   - **PDF/Word**：解析标题层级，按语义边界（章节、段落）切分而非固定 token 数硬切，保留标题作为 chunk 的 metadata，召回时注入上下文
   - **表格类**：不直接切碎——表头与每一行拼接成"表头+行"的文本块，或对表格生成自然语言摘要做向量化、原文做引用回溯
   - **扫描件/图片**：走 OCR pipeline，OCR 置信度低的进入人工校对队列（体现你对数据质量的成本意识）
   - **代码/API 文档**：按函数/类边界切分，保留完整代码块不被截断

3. **文件之间的关系处理（本题的加分点，多数人答不到）：**
   - **metadata 关联**：每个 chunk 携带文档 ID、章节路径、版本号、生效日期，支持"答案来自哪份文件哪一节"的溯源
   - **跨文档引用**：制度文件之间的引用关系（如"A 办法引用 B 规范第 3 条"）建成图关系或软链接，召回主文档时可级联带上被引用段落
   - **层级关系**：父子 chunk 策略——小块用于精准匹配，命中后回溯父块补全上下文（parent-document retrieval）
   - **版本与时效**：同一文档多版本时，按生效日期做优先级排序，避免旧制度被召回

**HR/面试官视角评价：**
- ✅ **加分信号**：能讲清"为什么这么分"而不是罗列工具名；提到溯源、时效、版本说明有真实业务场景意识
- ❌ **减分信号**：只说"用 LangChain 的 loader 加载"——说明是调包而非设计；完全没提 chunk 之间的关联，说明只做过 toy demo

## 第2题（项目深挖 · RAG 评估）

**题目：** 如何评估 RAG 系统的效果？具体遇到了什么问题？怎么解决的？

**考察点：**
- 是否建立过评估体系（有指标意识的产品 vs 凭感觉调优的产品）
- 问题定位能力：能否把"效果不好"拆解到检索/生成/数据的具体环节
- 闭环思维：评估 → 定位 → 优化 → 复验

**回答建议（产品经理角度）：**

1. **评估体系分两层讲：**
   - **离线评估**：构建标注好的 QA 测试集（gold set），分别测：
     - 检索侧：召回率 Recall@K、命中率（正确文档是否进 top-K）、MRR
     - 生成侧：答案忠实度（faithfulness，是否忠于检索内容不胡编）、答案相关性（answer relevancy）——可用 RAGAS 等框架，也可用更强模型做 LLM-as-Judge
   - **在线评估**：用户点赞/点踩率、答案采纳率、转人工率、badcase 收集机制

2. **遇到的真实问题 + 解法（按"现象 → 定位 → 解法"讲，这是 STAR 的变体）：**
   - **问题1：召回不准**——现象是答案答非所问；定位方法：把 badcase 拆成"检索就没召回对的"和"召回了但生成没用上"两类（关键动作！）；前者优化 embedding 模型/混合检索（向量+关键词 BM25）/query 改写，后者优化 prompt 和上下文组织
   - **问题2：切分破坏语义**——表格被切碎、跨页段落断裂导致答案残缺；解法：换语义切分、加 overlap、父子块策略
   - **问题3：多轮对话指代不清**——用户问"那它的价格呢"中的"它"无法解析；解法：query rewrite，结合对话历史把指代补全后再检索
   - **问题4：幻觉**——解法：prompt 强约束"仅根据给定资料回答，不知道就说不知道" + 输出引用来源让用户可验证 + 低置信度拒答转人工

3. **收尾强调闭环**：badcase 定期回归进测试集，形成"评估-优化-回归"的迭代机制，评估集随业务持续扩充。

**HR/面试官视角评价：**
- ✅ **加分信号**：能把"效果不好"二分定位到检索 or 生成（这是是否真做过的分水岭）；有量化指标而非"感觉变好了"
- ❌ **减分信号**：只会背 RAGAS 名词但说不出自己测试集怎么建的；问题与解法对不上（说了问题 A 却解了问题 B）

## 第3题（技术权衡 · 模型选型）

**题目：** 在一个 Agent 应用中，模型的成本、速度、效果之间如何平衡、选择和评估？

**考察点：**
- 产品思维核心题：AI 产品的本质是"效果-成本-体验"的不可能三角权衡
- 是否理解分层/路由架构，而非"全上最强模型"
- 有无真实的成本测算和体验量化意识

**回答建议（产品经理角度）：**

1. **先立框架**：这不是选"最好的模型"，而是**按任务分层做模型路由**：
   - 简单高频任务（意图识别、query 改写、格式化输出）→ 小模型/开源模型，成本低、延迟低
   - 复杂推理任务（多步规划、最终答案生成）→ 旗舰大模型
   - 中间档 → 中等模型 + 好 prompt 兜底

2. **三个维度各自如何量化：**
   - **成本**：token 单价 × 平均调用链长度（Agent 是多次调用的，要算单次任务全链路成本，不是单次 API 成本）× 日调用量 → 算出单任务成本和月度预算
   - **速度**：首 token 延迟（TTFT，影响体感）+ 端到端完成时长；明确业务场景的延迟容忍线（客服实时对话 < 3s vs 报告生成可异步）
   - **效果**：用第 2 题的评估集跑 benchmark，定"效果基线"——低于基线的模型直接出局，剩下的在成本和速度里选

3. **具体平衡手段（举项目里真实用过的）：**
   - 路由策略：先用小模型判断任务复杂度，简单的就地解决，复杂的升级大模型（model cascade）
   - 缓存：高频相似问题命中缓存直接返回，省调用又提速
   - Prompt 压缩/上下文裁剪：减少输入 token
   - 流式输出：不改总时长但显著改善体感速度
   - 异步化：非即时任务改异步 + 进度反馈，把速度问题转化为交互设计问题（产品经理特色答案）

4. **决策原则收尾**：先定效果基线（不可妥协的底线），再在达标模型里选成本最优的；成本超预算时优先砍"锦上添花"的调用环节，而不是降级核心链路的模型。

**HR/面试官视角评价：**
- ✅ **加分信号**：有"分层路由"思维而非单模型思维；能量化全链路成本；提到流式/异步这类产品化手段说明懂体验
- ❌ **减分信号**：直接答"用 GPT-x 效果最好"——没有权衡意识；说不清自己项目的单次任务成本

## 第4题（系统设计 · 从 0 到 1）

**题目：** 如何从头开始开发一套 Agent 系统？以及如何评估？

**考察点：**
- 系统观：能否讲清 Agent 的核心架构组件及协作关系
- 产品流程观：需求 → MVP → 迭代，而非一上来堆技术
- 评估是否覆盖"任务完成度"而不只是单轮对话质量

**回答建议（产品经理角度）：**

1. **先讲从需求出发，不是从技术出发（产品经理立场）：**
   - 明确场景：Agent 要解决什么任务？任务的输入输出、边界、容错要求是什么？
   - 判断"该不该用 Agent"：流程固定、步骤明确的任务用工作流（workflow）更稳；只有需要动态规划、工具选择不确定的才上 Agent 自主决策——这句是分水岭回答

2. **架构分层讲（从下往上）：**
   - **模型层**：大脑（LLM），负责任务规划与决策
   - **能力层**：工具集（Tools/API/检索），统一封装成标准接口供模型调用
   - **记忆层**：短期记忆（当前任务上下文）+ 长期记忆（用户偏好、历史任务沉淀）
   - **编排层**：规划（planning/ReAct）、反思（reflection）、多轮循环控制、异常兜底与人工接管
   - **交互层**：过程透明化（展示思考/执行步骤）、可打断可纠偏

3. **开发节奏**：MVP 先跑通单工具单任务的 happy path → 加工具和异常处理 → 上加护栏（guardrail：权限控制、危险操作二次确认、输出校验）→ 灰度上线收集 badcase 迭代

4. **评估（Agent 评估比 RAG 更难，要讲出差异）：**
   - **结果指标**：任务完成率（端到端成功率，最核心）、平均完成步数/耗时/成本
   - **过程指标**：规划合理性（轨迹评估，trace evaluation）、工具调用正确率、循环失控率（陷入死循环的比例）
   - **安全指标**：越权操作拦截率、幻觉导致的错误动作率
   - **方法**：仿真环境回放任务轨迹做离线评估 + 线上影子模式（Agent 输出只记录不执行，与人工结果对比）再逐步放量

**HR/面试官视角评价：**
- ✅ **加分信号**：先说"该不该用 Agent"说明有场景判断力；评估提到"轨迹评估"和"任务完成率"而非套用对话指标；提到护栏和人工接管说明有上线风险意识
- ❌ **减分信号**：架构只讲得出"调用大模型 API"；评估只说"让用户打分"

## 第5题（行为面试 · 科研能力）

**题目：** 遇到科研上的问题，你是如何解决的？

**考察点：**
- 问题解决的通用方法论（可迁移到工作场景）
- 独立攻坚能力 + 求助分寸感
- 顺丰此类问题在意的是：你能否把科研训练转化为工程/产品问题的解决能力

**回答建议（产品经理角度，用 STAR 结构 + 方法论提炼）：**

1. **准备一个真实案例**，按 STAR 讲：
   - **S/T**：科研中遇到的具体卡点（如实验结果不显著、方法不 work、数据不足）
   - **A**：拆解问题的过程——
     - 先**定位问题边界**：是假设错了、方法错了、还是执行错了？（对应做产品时的"先定位再解决"）
     - **文献调研**：这个问题是否已有成熟解法？站在前人肩膀上而非重复造轮子
     - **最小化实验**：设计小成本验证实验快速试错，而不是一次性大改
     - **求助策略**：自己卡了 X 天、试过 A/B/C 方案后，带着明确的假设和已排除的选项去请教导师/师兄——而不是空手去问（这点面试官很在意）
   - **R**：结果 + 量化（问题解决了，实验指标提升/论文产出）

2. **结尾提炼方法论并迁移**（加分动作）：
   - "科研训练给我最大的收获是面对未知问题的方法论：拆解 → 假设 → 验证 → 迭代。这套方法在我做 RAG 项目调优时同样适用——把'效果不好'拆解成检索和生成两个问题分别验证……"（回扣第 2 题，形成呼应）

**HR/面试官视角评价：**
- ✅ **加分信号**：有"带着已尝试的方案去求助"的细节，体现独立性与分寸感；能把科研方法迁移到产品工作
- ❌ **减分信号**：只讲"我很努力，天天泡实验室"——有苦劳无方法；求助=直接问答案

## 第6题（行为面试 · 团队协作）

**题目：** 遇到团队协作问题、有不同意见时你会怎么做？如果老师或师兄不同意你的（大）意见，你会怎么做？

**考察点：**
- 冲突处理能力：是对事还是对人
- 向上管理：面对权威（导师/师兄/未来的 leader）能否既坚持专业判断又尊重层级
- 顺丰文化偏务实执行，看重"能扛事、不内耗"的协作者

**回答建议（产品经理角度）：**

1. **第一层：平级分歧的处理原则**
   - 先区分分歧类型：**目标分歧**（要不要做）还是**路径分歧**（怎么做）——路径分歧求同，目标分歧回到用户/数据
   - 用数据和小实验说话：与其争论，不如快速做个低成本验证（A/B 测试、原型 demo），让结果做裁判
   - 对事不对人：复述对方观点确认理解无误后再表达异议（"我理解你的担心是 X，对吗？"）

2. **第二层：导师/师兄反对你的意见（本题核心，考察向上管理）**
   - **第一步：先理解，再辩解**——对方反对的原因可能掌握你不知道的信息（资源、风险、过往失败经验），先问清楚反对的点是什么
   - **第二步：区分"方向性反对"和"细节性反对"**——细节上服从经验；方向上如果仍坚持自己的判断，**用更充分的准备再沟通一次**：补充数据、调研、小范围验证结果，降低对方的决策风险
   - **第三步：明确边界后坚决执行**——如果最终决策权在对方且他已拍板，**保留意见但全力执行**（体现职业性）；执行中持续收集数据，用事实在合适时机再反馈
   - **底线意识（可提一句）**：除非涉及原则问题（学术诚信/合规/安全），否则尊重决策链

3. **收尾升华**：产品经理的日常就是在工程师、设计、业务方之间协调分歧——"分歧不可怕，可怕的是没有解决分歧的机制。我的原则是：小分歧用数据解决，大分歧升级给信息最全的人决策，决策后执行不打折。"

**HR/面试官视角评价：**
- ✅ **加分信号**："保留意见但全力执行"是成熟职场人的标志；提到"先理解对方反对的原因"体现同理心而非对抗姿态
- ❌ **减分信号**：表现出"我一般都是对的，最后证明他们对"的优越感；或者说"我会妥协听老师的"——显得没有独立判断。两种极端都扣分，**平衡感是本题的关键**

## 复盘与备考建议

| 维度 | 本场考察情况 | 后续备考动作 |
|------|------------|------------|
| RAG 技术深度 | 深挖文件处理、评估体系 | 补齐 graph RAG、混合检索的工程细节，准备 2-3 个量化 badcase 故事 |
| Agent 系统设计 | 架构 + 成本权衡 + 评估 | 梳理"全链路单次任务成本"的真实数字；准备 workflow vs Agent 的判断标准 |
| 行为面试 | 科研方法 + 协作冲突 | 按 STAR 打磨 1 个科研攻坚案例、1 个分歧处理案例，各准备 90 秒版和 3 分钟版 |
| 顺丰业务结合 | 本场未直接考 | 二面可能结合物流场景（客服 Agent、调度、知识库），提前把项目经验映射到顺丰场景 |

> **经验总结：** 一面业务面的本质是"验证简历真实性 + 产品思维摸底"。所有技术问题都要回答出"为什么这么做"的产品判断，所有行为问题都要体现"方法论 + 可迁移性"。
