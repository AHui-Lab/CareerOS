## 一、C/C++ 内存管理

### Q1: C 的 malloc/free 和 C++ 的 new/delete 有什么区别？

**参考口述答案**（按六点展开）：

> 主要有六个区别：
> ① **语言层面**：malloc/free 是 C 标准库函数；new/delete 是 C++ 的**运算符**，支持重载，可以自定义内存分配策略（比如做内存池）。
> ② **类型安全**：malloc 返回 `void*`，必须手动强转；new 返回具体类型指针，大小由编译器根据类型自动计算。
> ③ **构造与析构**：这是最核心的区别——malloc 只分配原始内存；new 会**先分配内存再调用构造函数**，delete 先调用析构函数再释放内存。对 POD 类型两者效果接近，对类类型完全不同。
> ④ **失败行为**：malloc 失败返回 NULL；new 失败默认**抛出 bad_alloc 异常**，除非用 `new (nothrow)` 才返回 NULL。
> ⑤ **数组配套**：`new[]` 必须配 `delete[]`，会逐个析构；malloc/free 没有数组语义。
> ⑥ **底层实现**：new/delete 通常基于 malloc/free 实现（运算符重载的默认版本）。
> 最后强调使用纪律：**malloc↔free、new↔delete、new[]↔delete[] 必须严格配对，混用是未定义行为**。

**追问链**：
- 「new 底层怎么做」→ operator new 分配内存（通常调 malloc）+ 类型化构造；operator new 可重载。
- 「new 出来的用 free 释放会怎样」→ UB：不执行析构，堆管理器元数据可能不匹配。
- 「malloc 底层实现」→ 小块用 brk 扩展堆顶 + 空闲链表/ bins 管理，大块（>128K）用 mmap 独立映射；分配带 chunk 头部元数据。
- 「嵌入式上怎么管理堆」→ 加分答案：「我倾向高频路径静态分配；必须动态时用固定大小内存池，避免碎片；加堆水位监控」（联动你的场景手册 14）。

### Q2: 为什么 free 之后要把指针置 NULL？不置会出什么问题？

**参考口述答案**：

> free 只把内存归还给堆管理器，**指针变量本身的值不变**，它还保存着那块内存的地址——这叫**悬挂指针（dangling pointer）**。不置 NULL 有两类风险：
> ① **二次释放（double free）**：代码后续路径再次 free 这个指针，会破坏堆的管理结构。glibc 会检测到报 "double free or corruption"；在没有这种检测的嵌入式环境，直接表现为堆损坏、偶发死机，而且离故障点很远、极难复现。
> ② **释放后使用（use-after-free）**：指针看起来有效，后续代码误以为它还指向合法数据去读写。最阴险的是刚 free 完那块内存内容还没被覆盖，**读出来的值"看起来是对的"**，bug 潜伏到这块内存被重新分配后才爆发，故障现象和根因隔很远。
> 置 NULL 之后的保护是双重的：第一，**free(NULL) 是标准保证的安全空操作**，double free 变成无害调用；第二，解引用 NULL 会**立刻崩溃**（段错误或 MCU 上的 HardFault）——故障点就是错误点，马上能定位。
> 一句话总结：**置 NULL 把"随机延时爆炸"变成"立即确定爆炸"**，是 fail-fast 设计思想。
> 再往上一层：C++ 用智能指针（unique_ptr/shared_ptr）从机制上消灭悬挂指针；我的嵌入式实践里则尽量静态分配，从源头减少 free 的使用场景。

**追问链**：
- 「free(NULL) 真的安全吗」→ 是，C 标准明确 free(NULL) 无操作。
- 「C++ 里 delete 后呢」→ 同样悬挂，delete 后也应置空；引出智能指针 RAII。
- 「怎么检测 use-after-free」→ valgrind / AddressSanitizer（host 端低成本验伤）。
- 「为什么 free 不知道指针长度却能正确释放」→ chunk 头部记录了块大小，free 按元数据归还。

**下次可能的变体**：内存泄漏怎么检测 / 野指针和悬挂指针区别 / 智能指针原理（shared_ptr 引用计数、循环引用要 weak_ptr）。

## 二、数据结构：链表

### Q3: 链表如何提高查找和删除操作的效率？

**破题框架**（先分操作、再给方案——AI 面试喜欢结构化开头）：

> 我先按操作拆开：链表的痛点是**查找 O(n)**；删除本身如果已知节点是 O(1)，但单向链表找前驱要 O(n)。所以"提效"分两个方向：
>
> **提高查找效率**：
> ① **哈希表做索引**：哈希表维护 key → 节点指针的映射，查找 O(1)；链表保留插入/顺序语义。代价是空间换时间。
> ② **跳表（Skip List）**：在有序链表上建多层索引，查找 O(log n)，实现简单且天然支持范围查询——Redis 的有序集合底层就是跳表。
> ③ 对嵌入式小规模场景：直接换**数组 + 下标**，利用缓存局部性反而更快——链表节点分散，cache miss 多，这是常被忽略的工程点。
>
> **提高删除效率**：
> ① **双向链表**：已知节点时删除 O(1)，不用找前驱；
> ② **哈希 + 双向链表组合**：查找 O(1) 定位节点 + 双向链表 O(1) 摘除节点——这就是 **LRU 缓存的标准实现**（LeetCode 146），也是嵌入式资源池/缓存的常用结构。
> ③ 惰性删除：先打标记，批量回收时统一摘链。

### Q4（追问）: 用哈希的话，如何保证索引的正确性？

这题你现场答得模糊，下面是完整弹药。「索引正确性」有四层含义，全说才算稳：

> **第一层：哈希函数把 key 映射到正确的桶，冲突时不能认错数据。**
> 哈希定位只是粗匹配，**桶内必须存完整 key 做精确比较**（存 key 本身而不只是 hash 值）——因为不同 key 可能 hash 相同，只比 hash 会误匹配。这就是"先 hash 定桶、再 key 精确比对"的两级查找。
>
> **第二层：冲突处理。**
> 拉链法（桶内挂链表/红黑树，Java HashMap 链表长度超 8 转红黑树）或开放地址法（线性探测/双重散列）。负载因子超阈值要扩容。
>
> **第三层：索引与链表本体的一致性——这是和上题结合的关键。**
> 哈希表存的是链表节点指针，那么链表做任何增删，**必须同步更新哈希表（双写）**：插入节点时同时写哈希条目；删除节点时必须先删掉哈希里的条目再释放节点内存。顺序反了就会出现**悬挂索引**——哈希返回一个已释放的指针，后续访问就是 use-after-free。这个和 free 后置 NULL 是同一类问题：指针有效性由谁保证。
>
> **第四层：扩容 rehash 时的一致性。**
> rehash 要重分布所有条目，期间读写会错乱。策略：一次性 rehash（短暂锁表）或**渐进式 rehash**（Redis 方案：新旧双表并存，每次操作搬一批，读时先查旧表再查新表）。

**加分句**：「嵌入式上我会用**静态节点池 + 哈希索引**代替动态分配，节点的生命周期由池管理，索引一致性用'先移除索引、后回收节点'的固定顺序保证。」

**下次可能的变体**：数组 vs 链表怎么选（答缓存局部性+内存池）/ 反转链表手写 / 判断链表有环（快慢指针）/ LRU 设计题。

## 三、网络编程：TCP Socket

### Q5: TCP Socket 通信会涉及哪些系统调用？

**参考口述答案**（背服务端五步 + 客户端三步）：

> **服务端**五个关键调用：
> ① `socket(AF_INET, SOCK_STREAM, 0)` —— 创建套接字，返回文件描述符；
> ② `bind(fd, 地址结构, len)` —— 绑定本地 IP 和端口；
> ③ `listen(fd, backlog)` —— 进入监听，内核创建**半连接队列**（收到 SYN、三次握手未完成）和**全连接队列**（握手完成的连接）；
> ④ `accept(listenfd)` —— 从全连接队列**取出一个已完成连接**，返回一个新的连接 fd；监听 fd 继续监听，连接 fd 用来收发数据；
> ⑤ `read/recv`、`write/send` 收发；`close()` 关闭。
> **客户端**：`socket()` → `connect()`（发起三次握手，阻塞至握手完成或超时失败）→ 收发 → `close()`。
> 辅助调用：`setsockopt`（如 SO_REUSEADDR 解决重启时端口占用）、`fcntl` 设非阻塞。

**必须讲出的加分认知**：「三次握手是**内核协议栈**完成的，不是 accept 完成的——accept 只是消费者，从全连接队列取货。」（多数候选人分不清这层）

### Q6（追问）: 调用 accept 时还没有客户端连接，内核怎么处理？

**参考口述答案**：

> 分两种模式：
> **默认阻塞模式**：当前进程被置为睡眠，挂到监听 socket 的**等待队列**上，不消耗 CPU；直到全连接队列来了新连接（或收到信号）才被唤醒，accept 返回新的连接 fd。
> **非阻塞模式**（fd 设置了 O_NONBLOCK）：accept 立即返回 -1，errno 置为 **EAGAIN / EWOULDBLOCK**，调用方需要轮询，或者更常见的，配合 IO 多路复用等待"监听 fd 可读"事件再调 accept。
> 补充一个安全相关点：半连接队列积压和 SYN flood 攻击有关，内核的 syncookies 机制可以缓解——说明我理解 accept 上下游的内核行为，而不只是背 API。

### Q7（追问）: 服务端要处理多个客户端连接，有什么方案？

**按演进讲**（结构最清晰，AI 评分友好）：

> 四代方案，逐代解决前一代的瓶颈：
> ① **多进程**：主进程 accept 后 `fork` 子进程处理连接，父进程继续 accept。隔离性好（一个崩不影响别人），但进程开销大、上下文切换贵；要注意父进程 close 连接 fd、子进程 close 监听 fd，并用 `wait/SIGCHLD` 回收僵尸进程。
> ② **多线程**：每个连接一个线程（`pthread_create`），共享地址空间、切换开销小，但需要同步保护共享数据；工程上用**线程池**避免频繁创建销毁。
> ③ **IO 多路复用**：单（少）线程监视一批 fd，就绪才处理：
>    - `select`：fd_set 位图，有 1024 个 fd 上限，每次调用要整体拷贝并重置集合，返回后 O(n) 遍历找就绪者；
>    - `poll`：pollfd 数组，去掉 1024 限制，但仍是 O(n) 遍历；
>    - `epoll`（Linux 特有）：内核用**红黑树**管理 fd、**就绪链表**回调通知，返回的就是就绪事件列表，O(1)；分 LT（水平触发，默认，不处理会反复通知）和 **ET（边缘触发，必须配非阻塞 fd 并读写到 EAGAIN，否则丢事件）**；海量并发下优势明显。
> ④ **事件驱动框架/Reactor**：libevent、libuv，把多路复用+回调封装成事件循环；高性能服务（Redis、Nginx、Netty 思想）的通用形态。
> 嵌入式视角：资源受限设备我更倾向**单线程 epoll/select + 每连接一个状态机**，避免线程栈的内存开销——这和我做协议解析状态机是同一套思路。

**手写小抄**（面试前确保能默写）：
```c
/* 服务端骨架 */
int lfd = socket(AF_INET, SOCK_STREAM, 0);
setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &one, sizeof(one));
bind(lfd, (struct sockaddr*)&addr, sizeof(addr));
listen(lfd, 128);
while (1) {
    int cfd = accept(lfd, NULL, NULL);   /* 阻塞直到有连接 */
    /* 多线程: pthread_create(handler, cfd)  或 epoll 事件循环 */
}
```

**下次可能的变体**：三次握手/四次挥手流程 / TIME_WAIT 为什么等 2MSL / recv 返回 0 什么意思（对端正常关闭）/ TCP vs UDP、UDP 上怎么做可靠传输（答：序号+ACK+超时重传+滑动窗口——和我 BLE 丢包测试的流水号是同一思想）/ select 和 epoll 区别单独考。

## 四、操作系统：进程与线程

### Q8: 进程和线程的区别？

**参考口述答案**（六个维度）：

> ① **本质定位**：进程是**资源分配**的基本单位，线程是 **CPU 调度**的基本单位。
> ② **地址空间**：进程地址空间独立；同一进程内的线程共享代码段、数据段、堆，各自拥有私有栈和寄存器上下文。
> ③ **切换开销**：进程切换要换页表基址、TLB 大面积失效、上下文大；同进程线程切换只换栈指针和寄存器，开销小得多。
> ④ **通信方式**：进程间要靠 IPC——管道、消息队列、共享内存、信号量、socket；线程间直接读写共享变量，配互斥锁、条件变量同步。
> ⑤ **健壮性**：进程隔离，一个崩溃不影响其他进程；一个线程崩溃整个进程挂掉。
> ⑥ **实现视角**：Linux 上线程是共享资源的轻量级进程（task_struct + CLONE_VM 等 clone 标志，NPTL）；RTOS 里的任务概念更接近线程——都在一个地址空间里调度。

### Q9（追问）: 进程和线程退出的时候有什么不同？（本题考得深，重点背）

**参考口述答案**（对照着讲最清楚）：

> **进程退出**：
> - 路径：`exit()` 会先执行 atexit 注册的清理函数、冲洗 stdio 缓冲，再陷入内核；`_exit()` 直接陷入内核。
> - 内核**整体回收**该进程的地址空间、页表、文件描述符等全部资源。
> - 关键点：进程退出后不是立刻消失，而是进入**僵尸态（Zombie）**——PCB 里保留着退出状态码，等**父进程 `wait()/waitpid()` 收割**；父进程不收，僵尸进程就一直占着进程表项，泄漏系统资源。
> - 父进程先死则变**孤儿进程**，被 1 号进程（init/systemd）收养并负责回收；退出时内核会向父进程发 SIGCHLD。
>
> **线程退出**：
> - `pthread_exit()` 或线程函数 return（注意：**主线程 return 会触发 exit 杀掉整个进程的所有线程**；主线程调 pthread_exit 则只退出自己，其他线程继续跑）。
> - 只回收线程**私有**资源：栈、寄存器上下文、TLS；**共享的堆和全局数据不动**——进程还活着。
> - joinable 线程退出后必须被 `pthread_join()` 回收（类似进程的 wait，还能取返回值），不 join 也会资源不释放；detached 线程退出后系统自动回收。
> - 线程退出**没有内建的"通知其他人"机制**，需要用条件变量/信号量自行协调。
>
> 一句话对照：**进程退出 = 整体回收 + 留退出状态等父进程 wait；线程退出 = 只收私有栈 + 等（或不等）同进程 join，共享资源不动。**

**下次可能的变体**：僵尸进程怎么避免（wait / SIGCHLD 处理 / 两次 fork）/ 进程间通信哪种最快（共享内存，但要信号量同步）/ 死锁四条件 / 虚拟内存与页表（嵌入式对照 MPU）。

## 五、硬件：电平转换

### Q10: 主控 3.3V、外设 5V，SPI 和 I2C 怎么做电平转换？

**破题**：先分析方向性，再给方案——这个开头本身就是得分点。

> 先看信号方向性，两种总线不一样：
> - **SPI**：SCK、MOSI、CS 是单向（主→从，3.3→5V），**MISO 单向（从→主，5V→3.3V）**——单向转换好办；
> - **I2C**：SDA/SCL 都是**双向开漏**，任何一端都可能把总线拉低——必须用双向方案。
>
> **方案一：专用电平转换芯片（首选，正规量产方案）**
> - 双电源供电的收发器：74LVC1T45 / 74LVC245（适合 SPI，方向引脚控制）；自动感方向的 TXS0108E / TXB0108；I2C 专用双向 **PCA9302**。高速 SPI（>10MHz）必须走这类。
>
> **方案二：MOS 管分立方案（I2C 经典电路）**
> 每根线一个 BSS138 + 两侧上拉（低电压侧上拉 3.3V、高电压侧上拉 5V）。成本最低，I2C 100k/400k 完全够用。原理见下一题。
>
> **方案三：电阻分压（只适用于 5V→3.3V 方向，如 SPI 的 MISO）**
> 串联分压把 5V 摁到 3.3V。代价：RC 时间常数限制速度（高速 SPI 不行）、有静态功耗、驱动能力弱。低速率、成本敏感场合凑合。
>
> **方案四：直连（先查手册，可能根本不用转）**
> - 5V 器件输出 → 3.3V 主控输入：看主控该引脚是否 **5V 容忍（FT）**——STM32 带 FT 标注的 GPIO 可以直接接 5V 信号；
> - 3.3V 输出 → 5V 器件输入：看 5V 器件 VIH，TTL 电平输入（VIH≈2.0V，如 74HCT 系列）可以直接驱动；CMOS 输入（VIH≈3.5V）则不行。
> - I2C 有个常用技巧：总线是开漏的，**上拉电阻直接接到 3.3V**，总线高电平就是 3.3V，只要 5V 器件的 VIH 低于 3.3V 就能直连——但要核对手册，不是所有 5V I2C 器件都满足。

### Q11（追问）: I2C 总线能不能用二极管做电平转换？

**参考口述答案**（结论先行）：

> **不能，核心原因是二极管是单向器件，而 I2C 是双向开漏总线。**
> SDA/SCL 上任何一方都可能拉低总线：如果串了二极管，3.3V 侧拉低时无法传导到 5V 侧（或反过来），另一边的器件根本"看得到"不了这个低电平——通信直接不成立。二极管方案只能考虑用在**已知单向**的信号上。
> 而且即使对单向信号，二极管串联方案也有第二个问题：**导通压降抬高低电平**。硅管 0.7V、肖特基 0.3V，低电平经过二极管后被抬高，接收方的 **VIL 噪声容限被吃掉**，一旦超过 VIL 上限，接收方把低电平识别成高电平或者处于不定态，通信错乱。
> **正确答案是 MOS 管电路**，它能双向工作的原理值得展开：
> - 以 BSS138 电路为例：栅极接 3.3V，源极接 3.3V 侧（3.3V 上拉），漏极接 5V 侧（5V 上拉）。
> - **静态**：两边都是高电平，Vgs = 0，MOS 截止，两边靠各自上拉维持，互相隔离，5V 不会倒灌 3.3V 侧。
> - **3.3V 侧拉低**：源极变 0，Vgs ≈ 3.3V > 开启电压，MOS 导通 → 漏极（5V 侧）被拉到低。
> - **5V 侧拉低**：MOS 的**体二极管**先导通，把源极拖到约 0.7V，此时 Vgs 足够使沟道导通，进一步把源极压到接近 0——两边都是低。
> 所以 MOS 方案天然双向、两边谁拉低都传导，这是它能用于 I2C 而二极管不行的根本原因。

**加分句**：「I2C 电平转换方案选型我会按成本和速率排序：直连（上拉拉 3.3V，先查 VIH）→ BSS138 分立 → PCA9302 专用芯片；速率和可靠性要求越高越往后靠。」

**下次可能的变体**：I2C 上拉电阻阻值怎么算（由 VOL 电流上限和总线电容决定的上升沿时间要求，常用 2.2k~10k）/ 为什么 I2C 开漏（线与仲裁+多主机+电平兼容，题库 02 已有）/ SPI 四种模式 / 3.3V 和 5V 逻辑电平标准数值（VIH/VIL/VOH/VOL）。
