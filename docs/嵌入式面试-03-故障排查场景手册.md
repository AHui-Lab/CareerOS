# 嵌入式面试 · 故障排查场景剧本（核心手册）

> 面试官问「讲一个你解决过的难题」时，考察的是**排查方法论**，不是运气。
> 本手册所有场景都绑定你的真实项目素材，统一使用「现象 → 分层排查 → 假设验证 → 根因 → 修复 → 沉淀」结构。
> 挑 3~4 个最熟的背到能脱口而出，其余混个脸熟（面试官换个现象你能现场推）。

---

## 〇、排查方法论总纲（开场可先说框架，非常加分）

遇到问题我先做三件事：

1. **分层定位**：物理层（电源/接线/电平）→ 链路层（波形/时序）→ 协议层（帧格式/校验）→ 应用层（算法/逻辑）。从下往上排查，先确认底层无脏再怀疑上层；
2. **对比与二分**：好板 vs 坏板、好路径 vs 坏路径做对比；代码二分（回退版本/注释模块）找引入点；
3. **最小复现 + 记录**：把偶发问题变成可复现的测试用例，全程打时间戳日志，用数据说话而不是猜。

仪器意识：万用表（电源/通断）、示波器（模拟波形/电源纹波）、逻辑分析仪（数字时序/协议解码）、串口日志 + LED/ GPIO 翻转指示程序跑飞位置。

## 场景 1：EKF 运行中偶发死机复位【HardFault · 栈溢出】★★★ 主推

**背景**（毕设）：STM32F407 上 EKF 融合定位联调阶段，长时间跑没事，但 UWB 数据密集到达时偶发死机/看门狗复位，复现概率约几小时一次。

**排查话术**：
> 最难的是偶发、低频。我先把 HardFault_Handler 改成保留现场：断点进去后发现压栈栈帧里的 PC 指向一个明显不属于任何函数的地址，同时读 SCB->CFSR 显示 STKERR（压栈错误）——怀疑是栈出了问题。再看 map 文件，任务栈只留了默认 0x400，而我在 EKF 更新函数里放了 4×4 float 矩阵的多个局部变量，加上中断嵌套时 ISR 的开销，临界情况下栈越界，写穿了栈底，破坏了相邻的 .bss 数据甚至向量表区域。
> 验证方法：我把栈底填成 0xA5A5A5A5 的 canary 模式，跑一段时间检查被改写的比例——确实栈溢出。修复：① 把 EKF 的矩阵全部改成静态分配（嵌入式上我倾向不用 malloc，避免碎片）；② 栈加大到 0x1000 并留 25% 裕量；③ 编译加 -fstack-usage 检查最深调用链。之后连续烤机 48 小时无复现。

**根因**：大局部数组 + 中断嵌套 → 栈溢出 → 向量表/相邻数据被破坏 → HardFault/复位。
**沉淀**：矩阵类缓冲一律静态分配；上电做栈 canary 自检；新驱动合入前看 stack usage 报告。

（技术点自查：能说出 SCB->CFSR/HFSR/BFAR 各自作用、map 文件里 stack 在哪、0xA5A5A5A5 填充法——题库 2.2 有。）

## 场景 2：UWB 数据帧偶发解析错帧【UART · 粘包/干扰】★★★ 主推

**背景**：多路 UART 接 UWB/IMU，测试中约千分之几的帧 CRC 错误，帧计数不连续，定位偶发跳变。

**排查话术**：
> 我分了两条线查：软件线和硬件线。软件上我把坏帧原始字节 dump 出来看，发现错误分两类：一类是帧中间被插入了别的字节（粘包/半包处理问题），一类是零星位翻转（干扰）。对第一类，我的解析原来是从缓冲区找帧头后线性读，改成严格状态机：找帧头→读长度→按长度收齐→验 CRC，CRC 不过整帧丢弃并计数，缓冲区指针复位，这样任何错帧不会污染下一帧。对第二类，用逻辑分析仪抓 UART 线，发现错帧时刻与电机启动时刻强相关——电机电刷噪声耦合进了信号线。硬件上加了磁珠和共地处理，软件上 CRC 计数做丢帧统计。最终帧错误率降到可忽略，且坏帧被隔离不再引起定位跳变。

**根因**：① 解析层没做状态机隔离错帧；② 电机 EMI 导致位错误。
**沉淀**：不定长协议接收的标准架构 = DMA 循环模式 + IDLE 空闲中断 + 环形缓冲 + 帧状态机 + CRC；坏帧计数器是链路质量的免费监测指标。

## 场景 3：IMU 初始化失败 / 总线无应答【I2C 卡死】★★

**背景**：I2C 接的传感器在整机上电时偶发读不到 ID 寄存器，逻辑分析仪看 SDA 一直被拉低。

**排查话术**：
> SDA 被从机拉死说明上一次通信异常终止，从机的移位寄存器还在等时钟把剩余位吐完，卡在「以为自己在传输」的状态。这是 I2C 的经典问题——如果主机在从机应答阶段复位或断电，就会留下这种悬挂状态。恢复方法：主机先发 9 个 SCL 时钟脉冲（用 GPIO 模拟），让从机把移位寄存器里的位移完，再发一个 STOP 条件释放总线；如果还不行就对外设断电重启。我在驱动里把「9 时钟恢复 + 总线重新初始化」写成了上电和通信超时后的标准恢复流程。另外排查了为什么会异常终止——发现是上电时序问题：传感器供电还没稳定，主机已经开始发地址，从机在欠压下应答混乱。把传感器电源就绪检测/上电延时加进初始化后，问题根除。

**根因**：上电时序竞争 → 从机应答异常 → 主机复位 → 从机锁死 SDA。
**沉淀**：I2C 驱动必备三级防御——上电延时/电源就绪检查、通信超时重试、总线卡死 9 时钟恢复。

## 场景 4：BLE 演示现场频繁断连【连接参数 + 2.4G 干扰】★★★ 主推（实习素材）

**背景**：合越智能做手套动捕演示，实验室稳定，到了有 WiFi 覆盖的现场，BLE 连接几分钟就断一次。

**排查话术**：
> 我先量化现象：日志里断连前都有 supervision timeout 超时——说明不是主动断开，是链路层在监督超时内没收到对方包。三个假设：① 连接参数太激进，密集数据 + 恶劣信道下丢包超时；② 2.4G 频段干扰，现场 WiFi 和 BLE 抢信道；③ 手机端省电策略杀后台。逐一验证：调整连接参数，把 connection interval 和 supervision timeout 拉开比例（timeout ≥ 6×interval 的工程经验值），断连率明显下降；再看信道——BLE 自带自适应跳频（AFH），但重扫环境后它需要时间把坏信道标记出去，我在连接建立后先跑一段低负载的握手再上业务数据，避开刚连接时的脆弱期；手机端关后台优化并加前台服务。三招之后现场连续演示一小时无断连。
> 这次让我建立了对 BLE 链路的三层认知：应用层数据节奏、连接参数、射频环境，排查断连要三层都看。

**根因**：连接参数裕量不足 + 现场射频干扰 + 终端省电策略叠加。
**沉淀**：演示/量产前的「现场射频体检」清单；连接参数按 timeout≥6×interval 配置。

## 场景 5：IMU 数据偶发大幅跳变【EMI / 数据异常剔除】★★

**背景**：割草机实车测试，IMU 输出偶尔出现单点大跳变，融进 EKF 后定位会抖一下。

**排查话术**：
> 先确认是「真跳变还是假跳变」：我把 IMU 原始数据带时间戳全量记录，和电机控制日志对齐——跳变时间点与电机大电流启动严格相关，说明是电磁干扰进了模拟前端/通信线，不是真实的运动。硬件上做了滤波和走线优化后仍偶发残余。所以软件兜底：在量测进入 EKF 之前加异常值门限——基于新息（innovation = 量测 − 预测）做卡方检验，新息平方除以 S（HPHᵀ+R）超过 3σ（卡方门限）的量测直接拒绝或降权，本周期靠预测顶住。加了这层后，即使偶发坏点也只表现为「这一拍没用上量测」，不会污染状态估计。
> 这也是鲁棒滤波的通用思路：滤波器要假设量测本身可能是坏的。

**根因**：电机 EMI → IMU 数据坏点 → 直接进 EKF 污染状态。
**沉淀**：所有外部量测进滤波器前过一致性检验（马氏距离/卡方）；时间戳对齐日志是定位「相关性」的关键工具。

## 场景 6：EKF 输出发散 / 定位漂移不收敛【滤波器调参】★★★ 主推

**背景**：第一次实车测试，纯仿真正常的 EKF 在实车上输出越飘越远，协方差越来越大。

**排查话术**：
> 我按「预测-量测-参数」三块排查。先把 EKF 输出和 UWB 原始解算同时画图对比：如果 EKF 跟着 UWB 走但慢半拍，是 Q/R 比例问题；如果不跟着走还发散，是模型或数值问题。当时看到的是第二种——发散。检查发现两个根因：一是轮式里程计在草地上打滑，速度被系统性高估，而我把 R 设得太小太信任它，错误信息持续拉偏状态；二是长时间只信预测时 P 矩阵对角持续增大，后来量测突然进来增益过大。修复：① 里程计观测的 R 在检测到轮速与 IMU/运动学不一致时动态放大（方差自适应）；② UWB 残差超限的基站观测降权；③ P 更新改用数值更稳的形式，并给 P 对角线设上下限防止病态。之后长时间跑车定位稳定，RMSE 数据就是在这个版本上测出来的。

**根因**：打滑导致系统性观测偏差 + R 配置过于信任 + 协方差无界。
**沉淀**：调 EKF 的顺序——先单传感器开环验证量测本身，再合滤波；Q/R 不是拍出来的，是拿残差序列统计调出来的。

## 场景 7：UWB 定位单点突跳【NLOS/多径】★★

**背景**：场地边角、有遮挡的位置，UWB 解算位置偶尔向前跳 0.5~1m。

**排查话术**：
> NLOS 下 UWB 信号经反射到达，测距偏大，解算位置被系统性拉偏。判别方法还是残差：正常视距下各基站距离残差都在噪声水平；NLOS 发生时，被遮挡那路基站残差显著变大，而其他路正常——这个不对称就是特征。处理：① 对单基站残差超 3σ 的观测降权或剔除，用剩余基站解算；② 基站级健康监测（滑动窗口错误率），持续异常的基站标记不可信，和「基站丢失自适应」同一套机制的温和版本；③ 高层逻辑上，运动学约束做一致性校验——载体速度有上限，位置突跳超物理可能的一律压住。最后在遮挡工况下定位不再突跳，代价是精度略降（少一路观测），但鲁棒性换精度是值得的。

**根因**：NLOS 多径 → 测距正偏 → 解算被拉偏。
**沉淀**：绝对量测（UWB）和运动约束（IMU/里程计）互相构成 sanity check，这是融合系统鲁棒性的本质。

## 场景 8：16 路电流采集读数不稳【ADC / 模拟前端】★★（研究生课题素材）

**背景**：晶圆检测的 16 路采集，静态标定时各通道读数末几位跳码，通道间还有固定偏差。

**排查话术**：
> 跳码我先分「共模噪声还是通道相关」。16 路一起跳 → 共模：查参考电压和电源纹波（示波器交流耦合看 VREF），加了去耦和更稳的基准后改善；单通道跳 → 通道相关：布线耦合/输入阻抗不匹配，输入端加 RC 一阶低通（截止频率按信号带宽留裕量），并确认 ADC 采样时间与信号源阻抗匹配（高源阻抗时采样保持电容充不满会偏低）。通道间固定偏差是系统性的，可以用标定消除：每通道注入已知标准信号，建 16 组增益/零偏校正系数，存 flash 上电加载。最终静态重复性达到了 Mapping 所需的指标。这件事让我建立了「模拟问题先分共模/差模、系统性误差靠标定、随机噪声靠滤波」的处理框架。

**根因**：基准纹波 + 源阻抗/采样时间不匹配 + 通道离散性。
**沉淀**：多通道采集必做三件事——VREF 纹波检查、源阻抗与采样时间匹配、逐通道增益零偏标定。

## 场景 9：采样时间间隔不均匀【中断延迟/抖动】★

**背景**：上位机曲线偶发「卡一下再跳两格」，检查发现 IMU 采样间隔偶发从 5ms 变成 8~10ms。

**排查话术**：
> 间隔抖动说明定时触发被延迟。我在采集时同时记录「硬件触发时刻」和「数据处理时刻」，发现触发间隔是均匀的，处理时刻抖动——说明不是定时器问题，是软件路径阻塞。排查中断优先级配置：UART 接收中断优先级低于另一个长耗时的打印/通信中断，被压后了。修复：① 重排优先级，数据采集链路（UART DMA 空闲中断、定时器）最高，日志打印降最低并把 printf 改成「写环形缓冲、主循环慢速吐出」；② ISR 里只做数据搬运和置标志，处理放主循环。之后间隔抖动小于一个时钟节拍。这里的关键排查手段是「同时记录硬件时间和软件时间」，把抖动定位到触发层还是处理层。

**根因**：低优先级数据中断被长 ISR 阻塞 + 阻塞式打印。
**沉淀**：ISR 只搬数据不处理；printf 异步化；关键链路优先级高于通信/日志。

## 场景 10：两个数据流共享缓冲，偶发一帧数据「撕裂」【并发/双缓冲】★

**背景**：上位机显示的传感器数据偶发一帧错乱：前半帧是旧数据后半帧是新数据。

**排查话术**：
> 典型的读写竞争：主循环在更新/读取共享缓冲时被中断打断，中断里又写了同一块缓冲。两个方案：一是互斥保护，但中断上下文不能上普通锁；二是无锁双缓冲——写者写后台缓冲，写完整帧后原子地交换指针（单变量指针赋值天然原子），读者永远读前台完整帧。我选了双缓冲+原子指针交换，因为我的场景是单写者单读者、整帧为单位，双缓冲零阻塞又无撕裂。如果是一对多或流式字节，就用环形缓冲单生产者单消费者模型。之后再无撕裂帧。这题让我搞清了「互斥」「无锁」「双缓冲」各自的适用形态。

**根因**：共享缓冲无同步 → 帧级撕裂。
**沉淀**：单生产者单消费者 → 环形缓冲；整帧消费 → 双缓冲+原子指针交换；复杂共享 → 互斥锁/关中断临界区（尽量短）。

## 场景 11：位移平台回零偶发撞限位 / 位置偏差【运动控制】★（研究生课题素材）

**背景**：晶圆扫描台某次回零时顶到机械限位触发急停，另有一次长时间运行后 Mapping 出现系统性位置偏移。

**排查话术**：
> 撞限位那次：回零逻辑是「高速找限位开关 → 反向慢速脱离 → 再低速二次确认」。日志发现第一次高速接近时开关信号有毛刺，提前触发后反向脱离距离不够，二次确认没生效就认为回零完成，坐标整体错了。修复：限位信号软件消抖（连续 N 次采样一致才认），回零必须完成「二段式确认」才算成功。系统性偏移那次：步进电机长行程丢步累积——加减速过猛。修复：梯形/S 形加减速曲线，并在每块晶圆开始前做一次「回零校验」：走到已知物理标记点核对坐标，超阈值立即停机报警。之后扫描上千行无撞机、无累积偏差。
> 这个场景我的总结是：开环系统必须有「绝对位置复核」机制，软件限位套在硬件限位里面，防呆不是可选项。

**根因**：限位信号毛刺 + 开环丢步累积。
**沉淀**：二段式回零+消抖；S 形加减速；周期性绝对位置校验；软件限位包络硬件限位。

## 场景 12：新板子上电不启动【最小系统排查】★

**背景**：新焊接的转接板，程序烧录成功但上电无输出。

**排查话术**：
> 最小系统四要素逐项排除：电源、时钟、复位、启动模式。万用表量各轨电压→正常；示波器看晶振起振波形（这步常被跳过，晶振不起振一切免谈）→发现 8MHz 晶振波形幅度异常，检查是两个负载电容焊反了型号；复位脚电平→正常；BOOT0→下拉正确。换电容后起振，板子跑起来。另外两个常见坑我也顺手检查了：SWD 烧录线过长导致下载不稳、某些封装 SWDIO 上拉缺失。我的习惯是把「电源-时钟-复位-boot」做成 checklist，5 分钟内走完，比瞎换器件快得多。

**根因**：晶振负载电容错料 → 不起振。
**沉淀**：上电不启动永远按最小系统 checklist 走；示波器看时钟是必做项。

## 场景 13：实验室正常、客户现场偶发通信失败【环境差异】★

**背景**：设备在实验室长期稳定，到现场（长线缆、多设备共电源）偶发通信失败。

**排查话术**：
> 现场和实验室三个差异：线缆长度（分布电容/衰减）、共地情况（地电位差）、干扰源密度。定位顺序还是从物理层开始：先共地——现场量两设备地间有交流电位差，光耦/隔离或单点共地解决地环路；再看长线信号质量，示波器看到边沿变缓，降低通信速率+加端接后眼图改善；最后协议层加重传和超时恢复兜底。三步之后现场稳定运行。这次教训是：实验室的「干净环境」会掩盖物理层裕量不足，量产设计前必须做恶劣工况测试（长线、共模干扰、电压拉偏）。

**根因**：地环路 + 长线信号完整性 + 无重传兜底。
**沉淀**：跨设备通信三问——共地了吗？线多长？断线怎么办（重传/超时/降级）？

## 场景 14：程序跑得越久越慢、最终复位【内存泄漏/碎片】★

**背景**：长时间烤机发现设备响应逐渐变慢，最终看门狗复位。

**排查话术**：
> 单调劣化指向资源泄漏。我在 host 平台上先复现：同样的协议解析代码在 PC 上跑，用 valgrind/ASan 检查，定位到异常帧处理路径上有一处动态分配的错误分支忘了释放。嵌入式侧确认：堆水位（剩余堆大小）单调下降曲线——实锤泄漏。修复错误分支后曲线平稳。更深一层我反思了架构：解析这种高频路径本就不该用动态内存，改成预分配的固定缓冲池。此后我把「堆水位监控 + 定期上报」做进了调试组件，泄漏类的劣化问题 10 分钟就能定位。
> 另外补充：即使无泄漏，长期 malloc/free 也会碎片化——嵌入式高频路径尽量静态分配或内存池。

**根因**：异常分支内存泄漏 → 堆耗尽 → 分配失败/性能劣化。
**沉淀**：高频路径禁动态内存；堆水位监控进调试组件；host 端 valgrind/ASan 是低成本验伤手段。
