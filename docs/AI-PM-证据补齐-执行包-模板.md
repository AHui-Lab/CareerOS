| 引用支持率 | 被引用原文**实际支持**的可核查主张数 / 带引用的可核查主张数 | 待测 |

**错误类型定义（分类必须一致，否则无法统计）：**

- `记忆召回`：该记得的没记得 / 记错了
- `拒答边界`：该拒绝的没拒绝 / 不该拒绝的拒绝了
- `延迟`：结果对但太慢（>5s），用户放弃

每个案例按此结构写，控制在 300 字内：

```

现象：<用户说了什么，期望什么，实际发生了什么>
```

## 模板 4：用户访谈提纲（每人 10 分钟）

**不要推销你的产品，只问他们现在的生活。**

```
1. 你现在记待办 / 记账 / 找资料，分别用什么工具？
   （追问）为什么要换过工具？上一个为什么不用了？

2. 上一次觉得麻烦是什么时候？具体卡在哪一步？
   （追问）当时你是怎么解决的？绕过去了还是算了？

3. 如果微信里有个人，你说一句话就能搞定，你最先想让它干哪件事？
   （追问）这件事你一周会做几次？

4. （现场演示后）你刚才说那句话的时候，期望它怎么回应？
   （追问）它现在这样回应，你会继续用第二次吗？为什么？

5. 有什么事是你绝对不想让一个 AI 助手自动帮你做的？
   （这一题测隐私与信任边界，答案很有价值）
```

### 访谈记录格式（每人一页）

```
受访人：            身份（同学/朋友/家人）：
日期：              与你的关系：

【原话记录】（尽量逐字，不要改写）
- 现在用什么：
- 麻烦在哪：
- 最想让它干的事：
- 不愿自动化的事：

【我观察到的问题】
【提炼出的需求】（写成用户结果，不写功能）
  ❌ 错误写法：「增加多端记忆功能」
  ✅ 正确写法：「用户换设备或隔几天继续时，助手仍记得已确认的事，且能查看和删除」
【是否进需求池】是 / 否，理由：
```

**目标：5–10 人。** 访谈原话是你以后所有「为什么这么设计」的答案源头。

## 模板 5：决策记录（ADR）——补上「放弃了什么」

> 每个项目补 3–5 条。这是「决策断裂」唯一的解法，也是面试里最容易被问、最难临时编的部分。

```markdown
## ADR-N：<决策主题>

日期：
状态：已决定 / 已推翻（被 ADR-M 取代）

### 背景
<当时面临什么问题，约束是什么>

### 考虑过的方案
| 方案 | 交付速度 | 复杂度 | 可靠性 | 成本 | 隐私风险 | 迁移成本 |
|---|---|---|---|---|---|---|
| A | | | | | | |
| B | | | | | | |

### 决定
选择方案 __。

### 理由
<为什么，用数据或明确事实支撑>

### 放弃了什么 / 代价
<明确写出代价，不要只写好处>

### 什么情况下会推翻这个决定
<这是成熟度的体现>
```

**龙虾助手与 RAG 项目建议先补这几条：**
1. 为什么用确定性工具执行业务动作，而不让模型直接改数据库
2. 为什么结构化业务数据放本机 SQLite，而知识放 GitHub/Obsidian
3. 为什么财务数据要 AES-256-GCM 加密且不同步到 GitHub
4. RAG 的相似度阈值为什么这么定（**没有实验依据就如实写「当前为经验值，待实验验证」**）
5. 为什么先做中心 Gateway 而不是先扩展更多能力
